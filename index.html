Caching

Caching — The Complete Concept Guide

1. Fundamentals

1.1 What Is a Cache?

A cache is a small, fast, temporary storage layer that keeps a copy of data so that future requests for that same data can be answered quickly — without repeating a slow operation (like reading from a database).

1.2 Why Cache?

Two problems drive the need for caching:

  • Speed (Latency): Reaching the original data source (database, remote server, external API). A cache sits closer, or holds a pre-computed answer, so the response comes back much faster.
  • Load / Cost: Every trip to the original source consumes resources — CPU cycles, database connections, network bandwidth, money (many APIs charge per call). If the same data is requested repeatedly, hitting the origin every time wastes resources. A cache absorbs repeated demand so the origin only has to do the real work once in a while.

Advantages of caching in general:

  • Reduces load on databases/services, which improves overall system stability
  • Improves scalability — a system can serve far more users with the same backend capacity

Disadvantages of caching in general:

  • Adds complexity (another moving part to design, monitor, and debug)
  • Introduces the risk of stale data (cache and source of truth can disagree)
  • Costs additional memory/storage
  • Can hide bugs — an issue at the origin might not appear until the cache expires, making debugging confusing

1.3 Source of Truth

The source of truth (or "origin") is the authoritative, and correct place where data actually lives — for example, a database. The cache is never the "real" data; it's always a copy that is supposed to reflect the source of truth.

1.4 Cache Hit / Miss

  • Cache Hit: The requested data is already present (and considered valid) in the cache. The system returns it immediately — no trip to the origin needed.
  • Cache Miss: The requested data is not in the cache (or it's there but expired/invalid). The system must go to the slower origin, retrieve the real data, return it to the requester, and — usually — store a copy in the cache for next time.
  • Hit Rate: The percentage of total requests that are hits. A high hit rate means the cache is doing its job well; a low hit rate means the cache isn't helping much (and may not be worth its complexity/cost).

1.5 Cache Entry

A cache entry is one single stored item inside the cache — typically made up of:

  • A key (an identifier used to look the data up, e.g., a user ID, a URL)
  • A value (the actual cached data/result)
  • Metadata — such as when it was created, when it expires (TTL), how often it's been accessed, etc., which the cache uses internally to manage eviction and expiration.
Key: user:123

Value: Ahmad's data

Metadata:
TTL = 5 minutes
Created = 21:00
Last Accessed = 21:03

2. Read Strategies

Read strategies define how data gets into the cache when it's read, and who is responsible for managing that flow.

→ If the data is not in the cache, who is responsible for retrieving it from the database?

2.1 Cache-Aside (a.k.a. "Lazy Loading")

How it works: The application itself is responsible for managing the cache.

  1. Application asks the cache for data (Request).
  1. Hit → return it.
  1. Miss → application goes to the database itself, fetches the data, then manually writes it into the cache, then returns it.

The cache is "beside" the application, not automatically in the data path — the app decides everything.

Advantages:

  • Only requested data ever gets cached (no wasted space on data nobody asked for)
  • Cache failure doesn't break the system — app can always fall back to the database
  • Simple model, widely used, flexible

Disadvantages:

  • Every miss involves two trips (check cache, then hit database) — slightly higher latency on a miss
  • Application code carries the caching logic — more responsibility on developers
  • Risk of stale data if the app forgets to update/invalidate the cache on writes

When to use: General-purpose caching for read-heavy workloads where you want full control (most common pattern — e.g., Redis/Memcached sitting beside a database).

When not to use: When you want caching to be transparent/automatic without touching application logic — then Read-Through is a better fit.

2.2 Read-Through

How it works: The application never talks to the database directly for reads. It only talks to the cache. The cache itself is responsible for going to the database on a miss, loading the data, storing it, and returning it — this logic sits inside the caching layer, not the application.

***this logic sits inside the caching layer

if cache miss
    go to database
    get data
    put data in cache
    return data

Advantages:

  • Cleaner application code — caching logic is centralized in the cache layer, not scattered through the app
  • Consistent caching behavior everywhere, since developers can't "forget" to check the cache

Disadvantages:

  • Requires a caching layer/library that actually supports this pattern (more infrastructure setup)
  • First request for any given item is still slow (a miss must load from origin)
  • Less flexible than cache-aside for special-case logic

When to use: Systems where you want caching to be invisible to application logic, and you're using a caching provider/library that natively supports read-through loading.

When not to use: Simple systems, or when you need fine-grained control over exactly what gets cached and how.

3. Write Strategies

Write strategies define what happens to the cache when the underlying data changes.

What does "underlying data" mean? data that is located in the primary source, such as a database

→When the original data changes, what will we do with the cache?

3.1 Write-Through

How it works: Every time data is written/updated, it's written to both the cache and the database at the same time, as part of the same operation, before the write is considered "done."

Advantages:

  • Cache is always consistent with the database — no stale reads
  • Simple to reason about correctness

Disadvantages:

  • Writes are slower, since two write operations happen every time (cache + database)
  • Data that's written but never read still takes up cache space (some waste)

When to use: Systems where data correctness/freshness matters more than raw write speed — e.g., financial data.

When not to use: High-throughput write-heavy systems where write latency is critical and slight staleness is tolerable.

3.2 Write-Behind (a.k.a. Write-Back)

How it works: Data is written to the cache immediately (fast), and the write to the actual database is delayed — done later, asynchronously, often in a batch.

→ When the data changes, write the change to the cache immediately, and let the database update happen later in the background.

Advantages:

  • Writes feel very fast to the user/application (cache write only)
  • Can batch multiple writes together, reducing database load

Disadvantages:

  • Risk of data loss if the system crashes before the delayed write reaches the database
  • More complex to implement correctly (needs a reliable queue/retry mechanism)
  • Temporary inconsistency between cache and database (by design)

When to use: Write-heavy systems where speed matters more than the tiny risk of loss, and where you can tolerate eventual (not immediate) persistence — e.g., analytics counters, activity logs, "like" counts.

When not to use: Anything where losing a write would be unacceptable — e.g., financial transactions, order confirmations.

3.2 Write-Around

What Problem Is Write-Around Solving?

Remember, a write strategy answers one question: "When data changes, what happens to the cache?"

We already covered two approaches:

  • Write-Through → update cache AND database at the same time, every time.
  • Write-Behind → update cache immediately, update database later (delayed).

Write-Around is a third, different philosophy: don't touch the cache during writes at all.

How Write-Around Actually Works, Step by Step

  1. New data comes in (someone updates or creates something).
  1. That data is written directly to the database — the source of truth.
  1. The cache is completely skipped during this write. It is not updated, not touched, nothing happens to it.
  1. Later, when someone reads that data:
    • The cache doesn't have it yet (because it was never written there) → cache miss
    • The system then fetches it from the database and now stores a copy in the cache, just like a normal miss would.

So the cache only ever gets filled up through reads, never through writes.

A Concrete Example

Imagine a system logging sensor readings from a factory machine, once every second:

temperature = 42.3   (written to DB every second)
temperature = 42.5   (written to DB every second)
temperature = 42.1   (written to DB every second)

Nobody is reading these values in real time — they're just being recorded for later analysis (maybe someone checks them once a month in a report).

With Write-Through, every single one of these writes would also update the cache — thousands of writes to the cache per day, for data that's almost never read. That's wasted effort and wasted cache space.

With Write-Around, these writes go straight to the database and skip the cache entirely. The cache stays empty for this data. Only when someone actually opens that monthly report (a read) does the relevant value get pulled from the database and cached — and only that specific value, not all the useless ones nobody asked for.

Why This Makes Sense: The Core Insight

Write-Around is built on a simple observation: not everything that gets written is going to be read again soon (or ever).

If you cache on every write (like Write-Through does), you waste cache space and cache-writing effort on data that might never be requested. Write-Around avoids that waste by being "lazy" — it only puts something in the cache once there's proven demand for it (i.e., someone actually asked to read it).

Advantages

  • No wasted cache writes — the cache is never polluted with data nobody ends up reading.
  • Faster writes compared to Write-Through, since only one system (the database) is updated, not two.
  • Efficient use of limited cache space — only "proven popular" (actually-requested) data occupies the cache.

Disadvantages

  • The first read after a write is always slow (a guaranteed cache miss), because the cache never got pre-filled during the write. This is the opposite of Write-Through, where a read right after a write would already be a hit.
  • If data is written and then immediately read very often, Write-Around performs poorly — you constantly pay the "miss" cost right after every write, gaining none of caching's benefit for that access pattern.

When to Use It

Use Write-Around when:

  • Data is written frequently, but rarely read again right after being written (logs, sensor data, audit trails, historical records).
  • You want to avoid cluttering the cache with data that's unlikely to be requested soon.

When NOT to Use It

Avoid Write-Around when:

  • Data is written and then read again almost immediately — e.g., a user updates their profile and then the app immediately reloads that profile to show a confirmation screen. In that case, Write-Around forces a guaranteed miss right when you least want one; Write-Through would perform much better here.

4. Refresh

4.1 Refresh-Ahead

How it works: Instead of waiting for an item to expire and then reloading it after a request comes in and misses (which causes one unlucky user to experience the slow path), the cache proactively refreshes popular items before they expire — usually triggered when an item is accessed close to its expiration time, in the background, without blocking the current request.

Advantages:

  • Popular/"hot" data almost never causes a slow miss for users — it's kept perpetually fresh in the background
  • Smooths out latency spikes that would otherwise happen right when items expire

Disadvantages:

  • Wastes work if data is refreshed but never actually requested again (guessing wrong about what's "hot")
  • Adds background-processing complexity
  • Requires predicting/tracking access patterns, which is non-trivial

When to use: For a small set of very "hot" (frequently accessed) items where consistently low latency matters a lot — e.g., a homepage banner, trending items list, top product catalog entries.

When not to use: For rarely accessed or unpredictable data — the wasted refresh work isn't worth it; plain TTL expiration is simpler and cheaper.

5. Expiration & Eviction

These are about deciding what leaves the cache, either because it's likely stale (expiration) or because there's no more room (eviction).

→These are two mechanisms that determine when and why data is retrieved from the cache.

We have two problems:

Problem 1: The data has stale. → Expiration

Problem 2: The cache is full. →Eviction

5.1 TTL (Time To Live)

How it works: Every cache entry is given a lifespan (e.g., "expires in 60 seconds"). Once that time passes, the entry is automatically considered invalid/stale and is either removed or refreshed on next access.

Advantages:

  • Simple to understand and implement
  • Guarantees data can't stay stale forever, even if nobody explicitly tells the cache "this changed"

Disadvantages:

  • Doesn't react to actual data changes — if data changes 1 second after being cached with a 60-second TTL, it stays stale for the remaining 59 seconds
  • Picking the "right" TTL is a guessing game: too short = many misses (less benefit); too long = more staleness risk

When to use: Data that changes at a roughly predictable pace, and where a small window of staleness is acceptable — e.g., weather data, news feeds, non-critical dashboards.

When not to use: Data where staleness is unacceptable even briefly (e.g., stock trading systems, real-time inventory during checkout) — needs explicit invalidation instead.

5.2 LRU (Least Recently Used)

How it works: When the cache is full and something new must be added, the entry that hasn't been accessed in the longest time gets evicted first. The assumption: if you haven't needed something in a while, you probably won't need it again soon.

→The cache is full, who should I delete?

Advantages:

  • Adapts naturally to changing access patterns
  • Works very well for most real-world workloads (recent activity tends to predict near-future activity)

Disadvantages:

  • Can be fooled by a one-time large scan (e.g., reading through a huge dataset once) which evicts genuinely "hot" data
  • Slightly more overhead to track "recency" of every entry compared to simpler policies

When to use: General-purpose caching — this is the most common, well-rounded default choice.

When not to use: When access frequency matters more than recency (e.g., a few items are accessed constantly but with occasional gaps) — LFU may perform better.

5.3 LFU (Least Frequently Used)

How it works: Evicts the entry that has been accessed the fewest total times, regardless of how recently. Favors consistently "popular" items over items that were just touched once recently.

Advantages:

  • Great at protecting genuinely popular, long-term-hot data from being evicted by a one-off burst of unrelated access
  • Reflects true "popularity" better than LRU in some workloads

Disadvantages:

  • New items start with a frequency count of zero/one, so they can get evicted quickly even if they're about to become popular ("cache pollution" of new-but-promising items)
  • More bookkeeping overhead (must track counts for every entry, not just recency)

When to use: Workloads with a stable set of consistently popular items — e.g., caching product info for best-sellers in an e-commerce catalog.

When not to use: Workloads where popularity shifts quickly and recent items matter more — LRU adapts faster.

5.4 FIFO (First In, First Out)

How it works: The cache behaves like a plain queue. Whichever item was added first gets evicted first, regardless of how often or recently it's been used since.

Advantages:

  • Extremely simple to implement, minimal overhead
  • Predictable behavior

Disadvantages:

  • Ignores actual usage patterns entirely — can evict something that's still being used heavily, just because it's "old"
  • Generally gives a worse hit rate than LRU/LFU in real workloads

When to use: Very simple systems where implementation simplicity matters more than optimal hit rate, or where all items genuinely have similar, short-lived relevance (e.g., a queue of temporary tokens).

When not to use: Any system where usage frequency/recency actually varies meaningfully between items — nearly always, LRU or LFU will perform better.

6. Consistency

6.1 Stale Data

Definition: Cached data that no longer matches the current, real data at the source of truth — because the source changed after the cache made its copy, and the cache hasn't caught up yet.

Why it matters: Stale data is dangerous specifically because it's invisible — the system doesn't error out, it just confidently returns the wrong answer. This makes it a common source of subtle, hard-to-diagnose bugs.

6.2 Cache Invalidation

Definition: The deliberate act of marking a cache entry as no longer valid (and removing or refreshing it) because the underlying data has changed.

Common approaches:

  • Time-based (TTL) — described above; passive, doesn't react to actual changes
  • Event-based/manual invalidation — the system that changes the data explicitly tells the cache "this specific item just changed, discard your copy," so the cache proactively removes just that one item

Advantages of proactive invalidation:

  • Much fresher data than pure TTL, since it reacts to real changes rather than waiting on a timer

Disadvantages:

  • Requires the writing system to remember to notify the cache every single time data changes — easy to miss in complex systems with many write paths
  • More engineering effort/coordination between services

When to use: Whenever staleness has real consequences and the system architecture allows write-paths to reliably notify the cache.

When not to use: In simple systems where a short TTL window of staleness is genuinely harmless — the added coordination complexity may not be worth it.

6.3 Eventual Consistency

Definition: A consistency model where the cache and the source of truth are allowed to disagree temporarily, but are guaranteed to converge (become equal) again eventually, given enough time without new updates.

This isn't a bug — it's a deliberate trade-off many systems accept in exchange for speed and availability. Most real-world caching (with TTL, write-behind, etc.) is eventually consistent by nature, not strictly/immediately consistent.

Advantages:

  • Enables much better performance and availability than trying to keep everything perfectly, immediately in sync
  • Practical and widely acceptable for most types of data

Disadvantages:

  • Different users/requests can briefly see different versions of the "truth" at the same time
  • Not appropriate for data where even momentary disagreement is unacceptable (e.g., double-spending money)

When to use: The vast majority of caching scenarios — social media feeds, product listings, search results, etc.

When not to use: Systems requiring strict/strong consistency, such as financial ledgers or systems handling unique, non-repeatable resources (e.g., seat booking where two people must not both get the same seat).

7. Cache Problems

These are failure modes that occur specifically because a cache exists — important to know so you can design around them.

7.1 Cache Stampede (a.k.a. "Thundering Herd")

What happens: A very popular cache entry expires. At that exact moment, a huge number of simultaneous requests all miss the cache at once and all hit the database simultaneously, trying to recompute/reload the same data — potentially overwhelming the database.

Mitigations:

  • Locking: Only let one request recompute the value; others wait for it to finish and reuse the result.
  • Refresh-ahead (see Section 4): refresh before expiration so this scenario never occurs for hot items.
  • Jittered TTLs: slightly randomize expiration times so many entries don't expire at the exact same instant.

When it's a real risk: High-traffic systems with a few extremely popular cache keys (e.g., a viral post, a flash-sale product page).

7.2 Cache Penetration

What happens: Requests repeatedly ask for data that doesn't exist at all (neither in the cache nor in the database) — e.g., someone querying an ID that was never valid, possibly maliciously (as an attack). Since it doesn't exist, it can never be cached, so every single request bypasses the cache and hits the database, defeating the purpose of caching entirely.

Mitigations:

  • Cache the "not found" result too (a "negative cache"), with a short TTL, so repeated lookups for the same nonexistent key don't keep hammering the database.
  • Bloom filters: a lightweight structure that can quickly tell you "this key definitely doesn't exist" before even checking the cache or database.

When it's a real risk: Public-facing APIs vulnerable to enumeration attacks, or systems with lots of "lookup by ID" traffic where invalid IDs are common.

7.3 Cache Avalanche

What happens: A large number of different cache entries expire at approximately the same time (e.g., they were all set with the same TTL and loaded in a batch at the same time), causing a massive simultaneous wave of misses that all hit the database at once — potentially crashing it. (Similar to a stampede, but across many different keys rather than one single hot key — and can also refer to the entire cache server/cluster going down at once.)

Mitigations:

  • Randomize/jitter TTLs so entries don't all expire in the same instant
  • Redundancy: run the cache as a cluster (multiple nodes) so one node failing doesn't wipe out the whole cache at once
  • Circuit breakers / rate limiting on the database to prevent it from being fully overwhelmed even if a wave does hit

When it's a real risk: Systems that load many cache entries in a batch job with identical TTLs, or systems relying on a single cache server/node with no redundancy.

8. Cache Placement / Types

This describes where in a system's architecture caching physically happens.

8.1 Browser Cache

What it is: Your web browser stores static assets (images, CSS, JavaScript files, sometimes whole pages) from websites you've visited, on your own device.

Advantages:

  • Zero network trip at all for a hit — as fast as caching can possibly be, since it's local to the user's device
  • Reduces load on the website's servers for every repeat visitor

Disadvantages:

  • Entirely outside the website owner's direct control (users can clear it, disable it, or have outdated versions)
  • Not shared between different users — everyone builds up their own separate cache

When to use: Static assets that don't change often (logos, stylesheets, script libraries).

When not to use: Highly dynamic, personalized, or sensitive content that must always be fresh or shouldn't persist on a shared/public device.

8.2 CDN Cache (Content Delivery Network)

What it is: Copies of website content are placed on servers physically distributed around the world, geographically close to users, so people don't all have to fetch data from one single, possibly far-away, central server.

Advantages:

  • Massively reduces latency for geographically distributed users
  • Absorbs huge amounts of traffic away from the origin server, improving resilience against traffic spikes
  • Often provides some protection against certain types of attacks (e.g., distributing/absorbing traffic floods)

Disadvantages:

  • Costs money (CDN services are usually paid, scaling with usage)
  • Adds a layer where invalidation/purging must be explicitly managed across many distributed nodes, which can be slower to fully propagate
  • Not ideal for highly personalized, per-user dynamic content

When to use: Static or semi-static content served to a geographically spread-out audience — images, videos, JS/CSS bundles, whole static pages.

When not to use: Content that's unique per user and changes constantly (e.g., a personal inbox), where caching provides little benefit and invalidation becomes very complex.

8.3 Application Cache

What it is: A running application/service keeps recently used or recently computed data directly in its own memory (or a nearby fast store), to avoid repeating expensive computations or database queries.

Advantages:

  • Very fast (often just in-process memory — no network call at all)
  • Simple to add for a single-server application

Disadvantages:

  • Not shared between multiple instances/servers of the same application — if you run 5 copies of an app, each has its own separate cache, which is memory-inefficient and can cause inconsistent answers between instances
  • Lost entirely if the application restarts

When to use: Single-instance applications, or data that's cheap to lose and rebuild, and doesn't need to be consistent across multiple servers.

When not to use: Multi-server/distributed applications where all instances need to see the same cached data — a Distributed Cache is the better fit.

8.4 Distributed Cache

What it is: A caching layer that runs as its own separate service (e.g., a dedicated cache cluster), shared across multiple application servers/instances, so they all see and use the same cached data instead of each keeping their own separate copy.

Advantages:

  • Consistent view of cached data across an entire fleet of application servers
  • Can be scaled independently of the application (add more cache capacity without touching app servers)
  • Survives individual application server restarts (cache itself is a separate, persistent service)

Disadvantages:

  • Requires a network call to reach it (slower than a purely in-process application cache, though still much faster than the origin database)
  • Adds another piece of infrastructure to deploy, monitor, and maintain
  • Becomes a new potential single point of failure if not run with redundancy/clustering

When to use: Any system running multiple instances of an application (which is the norm for most real, scaled systems) that need a shared, consistent cache — e.g., using Redis or Memcached as a shared caching layer.

When not to use: Very small, single-instance systems where the added infrastructure/complexity isn't justified by the workload.

Summary: How All the Pieces Fit Together in a Real System

A typical scaled web application often uses all four placement types at once, layered together:

  1. Browser cache holds static assets on the user's device (fastest possible, zero network).
  1. CDN cache holds static/semi-static content close to users geographically.
  1. Distributed cache (e.g., Redis) sits in front of the database, shared across all application servers, using a read strategy (cache-aside or read-through) and a write strategy (write-through or write-behind), managed with TTL + an eviction policy (LRU/LFU/FIFO), and protected against stampede, penetration, and avalanche with locking, negative-caching, and jittered TTLs.
  1. The database itself is the ultimate source of truth, with its own internal caching for frequently run queries.

Every design choice in this document is a trade-off between speed, freshness (consistency), complexity, and cost — there is no single "correct" answer; the right combination depends entirely on how the specific data is read, how often it changes, and how much staleness or complexity a given system can tolerate.
